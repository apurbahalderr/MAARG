MAARG (Golden Arrows) — ML + Routing Master Technical Plan
===============================================================

Purpose
-------
This document is the working master reference for the ML/routing side of
MAARG. It records what has already been completed, the current architecture,
the exact data/API contracts, what is intentionally synthetic for SIH Round 1,
what will be replaced with real data for later rounds, and the remaining
implementation plan.

The project is an AI-based early-warning and landslide/disruption-aware
logistics routing system for the North Eastern Region (NER).

The most important architectural principle is:

    Mappls generates feasible candidate routes.
    Model 1 predicts disruption risk.
    Model 2 predicts additional ETA delay.
    Backend makes the final route decision.
    Frontend displays the result and live updates.

Do not merge these responsibilities together.

4. MODEL 1 — WHAT IT DOES
================================================================

Model 1 is a tabular XGBoost classifier.

Its question is:

    "How likely is this analytical road segment to experience a
     disruption in the next 6 hours under the current conditions?"

Prediction unit:

    road segment x timestamp

Current training is synthetic data only.

Model 1 is NOT:
    a routing engine
    a GPS engine
    an image model
    an ETA model
    a Mappls model
    a final route selector

Model 1 receives 18 features.

Exact Model 1 features:

RAIN:
    rain_1h
    rain_6h
    rain_24h
    rain_72h
    rain_change_3h

SOIL:
    soil_moisture_surface
    soil_moisture_rootzone
    soil_moisture_delta_24h

TERRAIN:
    slope_mean
    slope_max
    elevation_change

HISTORICAL HAZARD:
    historical_landslide_count_1km
    historical_landslide_count_5km
    days_since_nearest_landslide
    historical_route_landslide_density

CURRENT INCIDENT:
    active_incident_count_1km
    active_incident_severity_score

CONTEXT:
    month

Model 1 produces:
    disruption_score in [0,1]

Operational bands:

    0.00 <= score < 0.25    LOW
    0.25 <= score < 0.50    MODERATE
    0.50 <= score < 0.75    HIGH
    0.75 <= score <= 1.00   CRITICAL

These are operational demo bands.
They are NOT calibrated real-world landslide probabilities.

================================================================
5. MODEL 1 — ROUTE RISK AGGREGATION
================================================================

Each analytical segment receives a disruption score.

A route may contain many segments:

    Route A:
        A0
        A1
        A2
        ...
        A72

The route risk is deliberately NOT a simple mean.

For every route calculate:

    mean_segment_risk
    p90_segment_risk
    max_segment_risk
    high_risk_segments
    critical_segments

Route risk:

    route_risk =
        0.50 * mean_segment_risk
        + 0.30 * p90_segment_risk
        + 0.20 * max_segment_risk

Clamp route risk to [0,1].

Critical segment:
    disruption_score >= 0.75

High segment:
    disruption_score >= 0.50

This protects against one dangerous segment being hidden inside a low
average.

Example:

    0.10
    0.12
    0.15
    0.95
    0.10

must explicitly identify the 0.95 segment as critical.

9. MAPPLS INTERNAL REQUEST CONTRACT
================================================================

MAARG internal representation should remain independent of Mappls's
query-string representation.

Use:

{
  "origin": {
    "lat": 26.1445,
    "lon": 91.7362
  },
  "destination": {
    "lat": 25.5788,
    "lon": 91.8933
  },
  "profile": "driving",
  "speedTypes": "optimal",
  "date_time": {
    "type": 0,
    "value": ""
  },
  "alternatives": 2,
  "avoid_locations": [],
  "avoid_polygons": []
}

Internal coordinate convention:
    lat = latitude
    lon = longitude

Only the Mappls adapter converts to Mappls's documented coordinate
ordering when making the provider request.

Mappls locations conceptually become:

    longitude,latitude;longitude,latitude

For the example:

    91.7362,26.1445;91.8933,25.5788

Candidate-route request should use origin + destination only when
alternatives are required.

Do not add unnecessary via points.

    primary route
    + up to 2 alternatives

Potential result:
    1 route
    2 routes

11. AVOIDANCE
================================================================

For a small number of dangerous road locations:

    avoid_locations

For broader affected zones:

    avoid_polygons

Internal coordinate representation stays:

{
  "lat": 25.5700,
  "lon": 91.8800

Provider-specific conversion happens inside the Mappls adapter.

MAARG does NOT send analytical 1-km segments to Mappls.

Mappls supports vehicle-aware routing features such as trucking and

The current implementation avoids inventing:

    height
    width
    length
    weight
    axle_load
    hazmat

If the backend later has real vehicle profile data, this can be added
to the Mappls request.

This remains a BACKEND/MAPPLS responsibility, not Model 1/Model 2.

================================================================
14. ROUTE SEGMENTATION
================================================================

Segmentation belongs to MAARG.

Mappls returns route geometry.

MAARG then:

    decode geometry
        ↓
    compute cumulative distance
        ↓
    create approximately 1-km analytical segments

These are analytical ML windows, NOT official Mappls road IDs.

A segment should contain information such as:

{
  "segment_index": 0,
  "start_km": 0.0,
  "end_km": 1.01,
  "start_coordinate": {
    "lat": 26.1445,
    "lon": 91.7362
  },
  "end_coordinate": {
    "lat": 26.1512,
    "lon": 91.7421
  },
  "geometry": [
    {
      "lat": 26.1445,
      "lon": 91.7362
    },
    {
      "lat": 26.1472,
      "lon": 91.7390
    }
  ]
}

The exact segment boundaries may vary slightly around 1 km.

Do not make one Mappls API request per segment.

The Mappls input-location limit has no impact on our internal analytical
segmentation because segmentation happens after route retrieval.

16. MODEL 2 — PURPOSE
================================================================

Model 2 answers:

    "How much additional travel delay should MAARG expect beyond
     the Mappls baseline ETA under current weather, terrain,
     incident and disruption conditions?"

Model 2 does NOT replace Mappls.

Model 2 predicts additional delay.

Core equation:

    adjusted_eta_minutes =
        mappls_baseline_eta_minutes
        + predicted_delay_minutes

The recommended target is:

    actual_delay_minutes

defined as:

    actual_delay_minutes =
        actual_segment_travel_time_minutes
        - mappls_baseline_eta_minutes

================================================================
17. WHY MODEL 2 IS SEGMENT-LEVEL
================================================================

A whole-route ETA model hides where delay originates.

Segment-level Model 2 allows:

    segment delay prediction
        ↓
    route delay = sum(segment delays)

This supports future:
    live ETA updates
    remaining-route ETA
    dynamic rerouting
    identifying where delay is building

30. FRONTEND → BACKEND → MAPPLS → ML — EASY FLOW
================================================================

A user selects:

    Origin
    Destination

Frontend sends that to Next.js backend.

Backend:
    1. receives origin/destination
    2. receives incident context if applicable
    3. asks Mappls for candidate routes
    4. receives route geometry + distance + duration
    5. normalizes route data
    6. passes candidate route information to ML

ML:
    1. creates/uses analytical segments
    2. gets or receives features
    3. Model 1 predicts disruption risk
    4. Model 2 predicts additional delay
    5. returns risk + ETA JSON

Backend:
    1. combines route risk and adjusted ETA
    2. applies operational rules
    3. chooses final route
    4. sends final route to frontend

Frontend:
    displays:
        selected route
        risk
        ETA
        warning
        fallback/alternative routes
        live state

31. FINAL BACKEND ROUTE DECISION
================================================================

This part is NOT currently owned by Model 1 or Model 2.

Backend should combine:

    disruption risk
    adjusted ETA
    route availability
    mission priority
    operational safety policy

MVP conceptual policy:

    CRITICAL route
        → reject or strongly penalize

    HIGH route
        → strong penalty

    LOW/MODERATE routes
        → compare adjusted ETA + risk

Possible scoring model for future backend implementation:

    route_score =
        0.65 * normalized_adjusted_eta
        + 0.35 * disruption_risk

Lower score is better.

This is only an initial operational policy.
Backend should own the final decision.
